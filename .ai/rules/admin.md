# Admin

## Breed belongsTo Species is scoped by SoftDeletes — breeds of a deleted species must be excluded, not just null-guarded
Species uses SoftDeletes, so Breed::species() (belongsTo) silently returns null for a breed whose species was soft-deleted, since Species' global scope excludes trashed rows (reading $breed->species->name directly throws "Attempt to read property on null"). Per product decision, such breeds must not appear in the "all breeds" list at all — App\Livewire\Admin\ManageBreeds::breeds() filters them out with ->whereHas('species') (the default Species scope makes this equivalent to "species not trashed"), so plain ->with('species') + $breed->species->name is safe there without a null-guard. Don't reintroduce ->withTrashed() on that relation/order-by subquery — it would bring back the null-species rows. See tests/Feature/ManageBreedsTest.php ("hides breeds whose species has been soft-deleted"). ManageBreeds::species() (the dropdown source) likewise never lists trashed species, including for a breed currently assigned to one.

## Create/edit forms use a single shared Flux modal per resource
ManageSpecies and ManageBreeds use one persistent `<flux:modal name="...">` (species-form / breed-form) reused for both create and edit, opened client-side via `<flux:modal.trigger name="...">` wrapping the row's Edit button or the page's Create button (each trigger also fires a `wire:click` to populate/reset the form fields server-side). After a successful save, the component closes it server-side with `Flux::modal('name')->close()` (dispatches a `modal-close` browser event — assertable in tests via `assertDispatched('modal-close', name: '...')`). Cancel buttons just wrap `<flux:modal.close>` and don't need a dedicated reset method.

Dropdowns (species filter, species picker in the breed modal) must exclude soft-deleted `Species` — don't special-case a currently-assigned trashed species back into the list; the `exists:species,id` validation rule still allows saving a breed whose species was soft-deleted after assignment, so editing/saving still works even though the dropdown won't show that option as selected.

## ManageVaccines: species is a many-to-many checkbox group, not a dropdown
Vaccine::species() (BelongsToMany via vaccine_species pivot, mirrors Sickness::species()) lets one vaccine apply to multiple species — unlike Breed's single belongsTo Species. App\Livewire\Admin\ManageVaccines binds a `vaccineSpeciesIds` array via `<flux:checkbox.group wire:model="vaccineSpeciesIds">` wrapping `<flux:checkbox value="{id}" label="{name}">` per species, validated as `array` + `vaccineSpeciesIds.*` => exists:species,id, and persisted with `$vaccine->species()->sync($validated['vaccineSpeciesIds'])` after the vaccine itself is saved (name has no DB-level unique constraint, unlike species/fur_types, so no uniqueness rule is applied). Vaccine uses Blameable + SoftDeletes already (added in the base migration, unlike Species/Breed/FurType which needed a follow-up migration) — deleteVaccine() soft-deletes. If ManageSicknesses is built next, follow the same checkbox-group-for-species pattern since Sickness::species() has the identical shape.

## All six admin lookup pages are now built (Shelters, Species, Breeds, FurTypes, Vaccines, Sicknesses)
App\Livewire\Admin\ManageSicknesses follows the exact ManageVaccines pattern (see [[admin]] rule on ManageVaccines): `flux:checkbox.group` bound to `sicknessSpeciesIds` for the Sickness::species() many-to-many, synced after save, plus a plain `sicknessDescription` textarea (nullable, stored as null when blank — Sickness::description is nullable). Sickness::species() and Vaccine::species() both now call ->withTimestamps() so sickness_species/vaccine_species pivot rows get created_at/updated_at (this was missing and had to be fixed after ManageVaccines shipped — don't drop it if refactoring either relation). No more sidebar placeholders (href="#") remain under Administration; all six global-lookup admin pages (admin.shelters/species/breeds/fur-types/vaccines/sicknesses) are wired to real Livewire components.

## ManageSizes added: seventh admin lookup, mirrors ManageBreeds
Size (sizes table: species_id belongsTo, name) was created without Blameable/SoftDeletes columns in the base migration, same gap Species/Breed/FurType had — fixed via a follow-up migration (2026_09_12_184645_add_soft_deletes_and_blameable_to_sizes_table) adding created_by/updated_by/deleted_by/deleted_at, same pattern as [[admin]] FurType/Breed notes. App\Livewire\Admin\ManageSizes (route admin.sizes.index, sidebar entry after Breeds) follows ManageBreeds exactly (species filter dropdown, ->whereHas('species') to hide sizes of soft-deleted species, order by species name then size name) but has no is_default-equivalent field — just species_id + name. Sizes has a nullable pets.size_id FK (RESTRICT) added alongside this table, not yet wired into PetForm/PetShow — do that in a follow-up if the size needs to be settable per pet.
