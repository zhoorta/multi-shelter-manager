# Models Livewire Pets Livewire Pets

## Pet vaccinations: schema, form, and pet-show table
pet_vaccines now has next_due_at (renamed from expires_at), lot_number, veterinarian_name, notes, plus deleted_by/soft deletes. Unlike the Species/Breed/FurType precedent (a follow-up migration on an already-run base table), these columns were folded directly into the pet_vaccines table definition inside the base migration (0001_01_01_000006_create_tables.php) — a deliberate exception, per explicit instruction, because this app isn't deployed yet and the next `migrate:fresh` picks up the base file as-is. Don't copy this pattern for other already-migrated tables without asking; the earlier follow-up-migration convention (see the Species/Breed/FurType migrations) still applies by default. PetVaccine (pivot) now uses SoftDeletes. Vaccine::pets() and Pet::vaccines() both withPivot the new columns.

App\Livewire\Pets\VaccinationForm (route pets.vaccinate, "pets/{pet}/vaccinate") is create-only (no edit/delete yet) — mirrors AdoptionForm's structure but without the optional-model/backRoute machinery since it's only ever reached from pet-show. Its vaccines() computed filters Vaccine by vaccine_species for the pet's species_id, same pattern as PetShow::sicknesses(). saveVaccination() uses $pet->vaccines()->attach() (not sync) since a pet can receive the same vaccine multiple times (annual boosters) — there's no unique constraint on (pet_id, vaccine_id).

"New Vaccination" is NOT in the heart dropdown (unlike Adoption/Sponsorship Registration) — that dropdown is hidden entirely when `$pet->status === 'adopted' && !$pet->is_sponsorable`, and vaccinations must stay reachable regardless of adoption status. Instead, pet-show.blade.php's Vaccinations table (always rendered, with a "No vaccinations registered" empty state) has its own header row with a "New Vaccination" button (`icon="plus"`, size sm) next to the `flux:label`, mirroring the sponsorship box's "Add Payment" button pattern. PetShow::mount() eager-loads 'vaccines' via orderByPivot('administered_at', 'desc'); the table lists Vaccine, Administered Date, Next Due Date, Lot Number, Veterinarian, Notes, plus an Actions column (Show, Edit, Delete). Show/Delete are handled directly in PetShow (no dedicated VaccinationShow route/page — there's no vaccinations index to link back to, unlike Adoption/Sponsorship); Edit reuses VaccinationForm itself.

VaccinationForm now supports edit like AdoptionForm: `mount(Pet $pet, ?PetVaccine $petVaccine = null)`, route `pets.vaccinate.edit` ("pets/{pet}/vaccinate/{petVaccine}/edit"), aborting 404 if the given PetVaccine's pet_id doesn't match the route pet. saveVaccination() branches on `$this->petVaccine !== null`: update() when editing (including reassigning vaccine_id, so the vaccine itself is editable, not just the other fields) vs. `$pet->vaccines()->attach()` when creating. The edit link in pet-show.blade.php's Actions column passes `$vaccine->pivot` (a PetVaccine instance) directly as the route param — implicit binding resolves it via getRouteKey() (id).

The Next Due Date cell in pet-show's vaccinations table is highlighted via an inline `@php` block per row (not a Computed property, since it only needs data already in the eager-loaded `$pet->vaccines` collection):
- **Red** (`bg-red-50 text-red-800 dark:bg-red-950/40 dark:text-red-200`) when the due date is strictly before today (`next_due_at->lt(now()->startOfDay())`) AND no other pivot row in `$pet->vaccines` has the same `vaccine_id` with a later `administered_at` — i.e. genuinely overdue and unresolved.
- **Amber** (`bg-amber-50 text-amber-800 dark:bg-amber-950/40 dark:text-amber-200`, same palette as the dashboard's misconfiguration warnings) otherwise, when `next_due_at->lte(now()->addWeek())` — covers due-within-a-week and exactly-a-week-away, and also an overdue dose that HAS since been re-administered (it stays amber, not un-highlighted, since the date itself is still in the past/near-term — only the red "unresolved" escalation is suppressed by a newer dose).

Test note: assert against the FULL class string (e.g. `'bg-red-50 text-red-800 dark:bg-red-950/40 dark:text-red-200'`), not a short substring like `'bg-red-50'` — Flux's own components elsewhere on pet-show also emit amber/red Tailwind utility classes, so a short substring search over the full response body produces false-positive matches.

**Pivot primary key trap**: Pet::vaccines()/Vaccine::pets() must include `'id'` in `withPivot([...])` or `$vaccine->pivot->id` silently reads as null (no error — PHP just null-coerces it, which surfaced as a TypeError deep in Livewire's method-call binding when passed to a typed `int` parameter). This bit the Show/Delete actions below, since they're the first vaccine-pivot code needing the pivot's own row id rather than just its scalar columns. Pet::sicknesses() has the same gap (no 'id' in its withPivot) but nothing currently needs that pivot's id — if you add one, add 'id' there too.

PetShow::deleteVaccination(int $petVaccineId) scopes via `PetVaccine::query()->where('pet_id', $this->pet->id)` (PetVaccine has a direct pet_id column, unlike Sponsorship/SponsorshipPayment which need whereHas — see scopedPetVaccineQuery()), then soft-deletes and calls refreshVaccines() to reload the relation. The "Show" action needs no Livewire method at all — it's a per-row `flux:modal` reusing data already in the eager-loaded `$pet->vaccines` collection, triggered by `flux:modal.trigger name="vaccination-show-{id}"`; Delete follows the sponsorship-payment confirm-modal pattern (`confirm-vaccination-deletion-{id}`).
